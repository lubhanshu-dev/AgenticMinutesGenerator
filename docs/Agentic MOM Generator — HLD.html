1. Purpose

This document describes the high-level architecture of an agentic system that records a meeting locally, transcribes it live, identifies speakers, and generates a structured Minutes-of-Meeting (MOM) document. It defines system scope, component responsibilities, data flow, interface contracts, non-functional requirements, and the strategy for local-vs-cloud LLM execution.

3. Scope

3.1 In Scope — v1

# Capability Notes
1 Record voice from local mic Single device, single active session at a time
2 Live speech-to-text Streaming, partial + final transcript
3 Summary generation Post-meeting (optionally incremental)
4 Structured MOM generation Agenda, decisions, action items, owners
5 Speaker diarization Unsupervised clustering per session
6 Person identification Optional match against locally-enrolled voice profiles
7 Local-first execution Local models by default, no mandatory network egress
8 Cloud LLM fallback Opt-in, redaction-gated, used only when local inference fails or falls below a quality threshold
9 Pause / resume recording User-triggered
10 Auto-sleep on silence System-triggered, auto-wake on speech
11 Monitoring & evaluation Operational health metrics + output quality evaluation (see §7.4)

3.2 Out of Scope — v1 (Phase 2 candidates)

  • Multi-tenant / multi-session concurrent scaling (shared server, many simultaneous users)
  • Cross-meeting persistent identity beyond the local profile store
  • Multi-device sync / collaborative live dashboard
  • Third-party export integrations (Slack, Notion, email)

3.3 Clarified Interpretations

  • "Scalability for multiple users talking" → multi-speaker diarization within a single session, not horizontal service scaling.
  • "100ms performance" → applies to the live partial-transcript path only, not batch summary/MOM generation.
  • "Local first" → local execution is the default and the fallback path is cloud, never the reverse. Cloud is opt-in per session, not silently enabled.

4. Architecture Principles & Patterns

Standard software design practices applied throughout:

  • Single Responsibility Principle — every class listed in §6 owns exactly one concern.
  • Dependency Inversion — high-level agents (SummaryGeneratorAgent, MOMGeneratorAgent) depend on the ILLMProvider interface, not on a concrete LLM backend. This is what makes the cloud fallback pluggable without touching agent logic.
  • Strategy Pattern — LocalLLMClient and CloudLLMClient are interchangeable strategies behind ILLMProvider; LLMRouter selects between them at runtime.
  • Circuit Breaker Pattern — LLMRouter trips to cloud (if permitted) after repeated local failures/timeouts, and resets once local recovers, preventing cascading stalls.
  • Repository Pattern — all persistence goes through MeetingRepository; no component talks to SQLite/filesystem directly.
  • Observer / Pub-Sub — components communicate via EventBus, not direct method calls, keeping them independently testable.
  • Separation of ops-monitoring vs. quality-evaluation — treated as two distinct concerns (§7.4), each with its own component, per standard MLOps practice.

6. Component Responsibilities (SRP)

6.1 Capture & Transcription Pipeline

Class Responsibility Depends on
AudioCaptureService Opens mic stream, chunks PCM into ~200–300ms frames, honors pause/resume OS audio API
AudioBufferManager Thread-safe ring buffer feeding downstream consumers without blocking capture AudioCaptureService
VoiceActivityDetector Classifies each frame as speech/silence AudioBufferManager
SleepController Tracks silence duration; triggers auto-sleep / wake VoiceActivityDetector
StreamingTranscriber Wraps local streaming ASR model; emits partial + final segments with timestamps AudioBufferManager, ASR model
SpeakerDiarizer Computes voice embeddings per segment, clusters into distinct speakers AudioBufferManager
SpeakerProfileStore Persists/retrieves named voice-embedding profiles Local DB
TranscriptAggregator Merges ASR output + speaker labels into one ordered transcript StreamingTranscriber, SpeakerDiarizer
SessionStateManager Single source of truth for session lifecycle (idle → recording → paused → sleeping → ended) EventBus

6.2 Generation & Orchestration

Class Responsibility Depends on
MeetingOrchestratorAgent Decides when to invoke summarization/MOM generation based on session state; handles retries and partial-failure recovery SessionStateManager, SummaryGeneratorAgent, MOMGeneratorAgent
SummaryGeneratorAgent Produces a narrative summary from the transcript ILLMProvider (via LLMRouter)
MOMGeneratorAgent Produces structured MOM (agenda, decisions, action items + owners) via constrained prompting ILLMProvider (via LLMRouter)

6.3 LLM Provider Layer (Local + Cloud Fallback)

Class Responsibility Depends on
ILLMProvider (interface) Defines generate(prompt, params) -> response contract —
LocalLLMClient Implements ILLMProvider over a local runtime (e.g., Ollama/llama.cpp) Local LLM runtime
CloudLLMClient Implements ILLMProvider over an external API; only ever invoked by LLMRouter, never called directly by agents External LLM API
LLMRouter Chooses local vs. cloud per call: local by default; falls back to cloud only if local fails/times out and ConsentManager confirms the session has opted in; applies circuit-breaker logic to avoid repeated slow failures LocalLLMClient, CloudLLMClient, ConsentManager, PIIRedactionService
PIIRedactionService Strips/masks names, emails, phone numbers, and enrolled-speaker identities from any payload before it is allowed to leave the device —
ConsentManager Tracks per-session user consent for cloud fallback; default is off MeetingRepository

6.4 Persistence & Security

Class Responsibility Depends on
MeetingRepository Persists transcripts, summaries, MOM docs, audio; sole owner of storage access (Repository pattern) Filesystem + SQLite
SecurityManager Encryption at rest, access control, redaction hooks before any external call MeetingRepository, SpeakerProfileStore

7. Non-Functional Requirements

7.1 Scalability

SpeakerDiarizer handles multiple simultaneous speakers via per-frame embedding + clustering, independent of transcript generation. The orchestrator is stateless-per-session, so running multiple sessions in parallel (Phase 2) means instantiating more pipeline instances, not redesigning them.

7.2 Security & Privacy

  • Local execution is the default; no network egress unless ConsentManager confirms opt-in.
  • PIIRedactionService runs before every cloud call — no exceptions, enforced at the LLMRouter level so agents cannot bypass it.
  • SecurityManager encrypts transcripts, audio, and voice profiles at rest.
  • Cloud fallback is logged (LLMFallbackTriggered event) so the user can audit when and why data left the device.

7.3 Performance

  • Live transcript path: small frame sizes (~200–300ms), lock-free ring buffer, VAD gating to skip silent frames, async event-driven push rather than polling — target <100ms frame-to-partial-transcript latency.
  • Batch generation (summary/MOM) is explicitly excluded from the 100ms budget; it is measured separately under §7.4.

7.4 Monitoring & System Evaluation

This NFR has two distinct halves, tracked by separate components per standard MLOps practice — operational health is not the same concern as output quality:

a) Operational Monitoring (is the system running correctly?)

  • MetricsCollector tracks per-component latency, throughput, and resource usage.
  • HealthCheckService performs liveness checks on each pipeline stage and flags stalled components (e.g., ASR thread hung, LLM call timing out).
  • AlertManager raises threshold-based alerts (e.g., sustained >100ms transcript latency, elevated cloud-fallback rate, repeated local LLM failures).
  • All logs are structured and local by default, consistent with the local-first NFR.

b) Output Quality Evaluation (is the system producing good results?)

  • EvaluationService periodically scores:
    • ASR accuracy via WER against sampled/labeled audio.
    • Diarization accuracy (speaker confusion rate) where ground truth is available.
    • Summary/MOM quality via rubric-based scoring (completeness of action items, correctness of owners/dates).
  • FeedbackCollector captures user corrections to a generated MOM (edits, deletions, added action items) as a continuous quality signal and as regression fixtures for future model/prompt changes.
  • Evaluation results feed back into AlertManager if quality drops below a defined baseline (e.g., MOM completeness score drifts down after a model/prompt change).

7.5 Reliability

  • MeetingOrchestratorAgent persists intermediate state (partial transcript, diarization labels) via MeetingRepository continuously, so a crash mid-meeting does not lose captured data — the session can resume from last checkpoint.
  • Circuit-breaker logic in LLMRouter prevents a failing LLM backend from stalling the whole pipeline.

7.6 Maintainability

  • Strict SRP + interface-based dependencies (§4) mean each class is independently unit-testable and mockable, and the LLM backend can be swapped or a new provider added without touching agent or orchestrator code.

8. Sequence Flow — Meeting with Cloud Fallback

sequenceDiagram
    participant MOA as MeetingOrchestratorAgent
    participant MGA as MOMGeneratorAgent
    participant Router as LLMRouter
    participant Consent as ConsentManager
    participant PII as PIIRedactionService
    participant Local as LocalLLMClient
    participant Cloud as CloudLLMClient
    participant Eval as EvaluationService

    MOA->>MGA: generate MOM(transcript, summary, speakers)
    MGA->>Router: generate(prompt)
    Router->>Local: generate(prompt)
    alt local succeeds
        Local-->>Router: structured MOM
    else local fails or times out
        Router->>Consent: is cloud fallback allowed?
        alt consent granted
            Router->>PII: redact(prompt)
            PII-->>Router: redacted prompt
            Router->>Cloud: generate(redacted prompt)
            Cloud-->>Router: structured MOM
        else consent not granted
            Router-->>MGA: failure (no fallback permitted)
        end
    end
    Router-->>MGA: result
    MGA-->>MOA: structured MOM
    MOA->>Eval: log output for quality evaluation

11. Risks & Mitigations

Risk Mitigation
Cloud fallback silently leaks data Redaction is enforced inside LLMRouter, not left to agents; fallback requires explicit per-session consent, default off
Local LLM quality insufficient for MOM structure EvaluationService tracks completeness score; persistent drift triggers alert to consider prompt/model tuning before defaulting to cloud
Diarization errors on overlapping speech Flagged in evaluation metrics (speaker confusion rate); acceptable-error threshold should be defined with stakeholders
